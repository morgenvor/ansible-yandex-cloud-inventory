# Отличия форка от upstream

Форк [morgenvor/ansible-yandex-cloud-inventory](https://github.com/morgenvor/ansible-yandex-cloud-inventory)
основан на [mzatolokin/ansible-yandex-cloud-inventory](https://github.com/mzatolokin/ansible-yandex-cloud-inventory)
(ветка `main`, коммит `d2ad1ab`, автор Maksim Zatolokin, лицензия MIT).
Upstream-автор неактивен около года, поэтому исправления выпускаются из форка.

Этот документ — публичный список отличий: что было в upstream, что стало здесь и
что нужно поменять при переходе. Версия форка — `3.0.2`.

## 1. Исправления поведения (появились в 1.0.1)

| # | Было в upstream | Стало в форке |
|---|---|---|
| 1 | `ansible_host` брался из внутреннего IP | `ansible_host` — публичный IP, если он есть; внутренний остаётся в `private_ipv4` |
| 2 | `verify_file` принимал любой `*.yml`/`*.yaml`, чужой inventory ломался с «Incorrect plugin name» | принимаются только `yc_inventory.yml`/`yc_inventory.yaml` и `*_yc_inventory.yml`/`*_yc_inventory.yaml` |
| 3 | читалась только первая страница `ListInstances` (100 ВМ), остальные терялись | постраничный обход по `next_page_token`, `page_size=1000` |
| 4 | ВМ без сетевых интерфейсов роняла плагин с `IndexError`, Ansible отдавал пустой inventory | ВМ пропускается с предупреждением, остальные хосты на месте |
| 5 | дефисы заменялись на `_` и в ключах, и в значениях меток (`web-app` → `web_app`) | значение не меняется, нормализуется только ключ |
| 6 | имя ВМ писалось в переменную `name` — Ansible ругался «Found variable using reserved name» | переменная называется `yc_name` |
| 7 | `ansible: false` сравнивалось с учётом регистра | сравнение без учёта регистра (`False`, `FALSE` тоже работают) |
| 8 | дефисы заменялись на `_` и в именах хостов, поэтому `web-1` и `web_1` давали один хост, а `ansible web-1` не находил ВМ | имя хоста — имя ВМ как есть; нормализуются только зоны (имена групп) и ключи меток |
| 9 | метка `ansible_group` ставила ВМ в группу с любым именем (`docker`, но и `../../outside/evil`) | группа из метки создаётся только как `yc_<значение>` (`docker` → `yc_docker`), `-` → `_`, иначе предупреждение и группа не создаётся |

## 2. Изменения контракта меток (2.0.0)

Метки ВМ — недоверенный ввод: поставить их может любой, у кого есть доступ к
каталогу. До 2.0 метка попадала в переменные хоста «как есть», то есть метка
`ansible_host` подменяла адрес подключения, а `ansible_ssh_common_args` с
`ProxyCommand` выполняла произвольную команду на контроллере.

В 2.0 метки больше не могут переопределить служебные переменные:

| Что | Было (1.x) | Стало (2.0) |
|---|---|---|
| метка `role: web-app` | переменная `role = web-app` | `yc_label_role = web-app` |
| метка `owner-team` | переменная `owner_team` | `yc_label_owner_team` |
| метка `ansible_host: 203.0.113.99` | подменяла адрес подключения | `yc_label_ansible_host`, `ansible_host` = реальный IP, предупреждение |
| метка `ansible_ssh_common_args` | становилась переменной хоста | только `yc_label_ansible_ssh_common_args`, предупреждение |
| метка `ansible_user` | применялась | применяется (белый список) и дублируется как `yc_label_ansible_user` |
| метка `ansible_port` | применялась | применяется (белый список) и дублируется как `yc_label_ansible_port` |
| метка `ansible_group` | директива группировки | директива; группа создаётся как `yc_<значение>` (см. §1, п. 9) |
| метка `ansible: false` | фильтр | без изменений (фильтр) |
| метка `ansible-group` (через дефис) | переменная `ansible_group`, группы не было | та же переменная и та же директива: группа `yc_docker` (ключи нормализуются до чтения директив) |
| значение `ansible_port: not-a-port` или `ansible_user` с пробелом | применялось как есть, `ssh` падал на разборе `-o Port=…` / `-o User="…"` | предупреждение с причиной, значение не применено, остаётся в `yc_label_*` |

Белый список — `ansible_user` и `ansible_port`: без них плагин терял бы
возможность управлять учётной записью подключения, а эти две переменные не
выполняют код на контроллере. Остальные `ansible_*`-метки остаются доступны как
`yc_label_*` и сопровождаются предупреждением с именем ВМ и ключом.

Отдельно про `ansible_user`: это переменная хоста, поэтому она **перебивает**
`remote_user` в плейбуке и `-u` в командной строке. Приоритет задаёт сам
ansible-core (`play_context.set_task_and_variable_override()`: сначала
применяются атрибуты задачи, затем magic-переменные из инвентаря), плагин его
не меняет — но метку с этим ключом ставьте осознанно.

### Про ограничения меток в самом Yandex Cloud

По документации Yandex Cloud значения меток ограничены: до 63 символов,
строчные латинские буквы, цифры, `-` и `_`
([Метки ресурсов сервисов](https://yandex.cloud/ru/docs/resource-manager/concepts/labels)).
Если бы проверка соблюдалась всегда, значения вида `../../outside/evil` или
`web.dev` до плагина не доходили бы. Но полагаться на неё нельзя: в живом
прогоне 2026-11-01 API принял метку `ansible_group=../../outside/evil`, и
`tests/live-check.sh` зафиксировал предупреждение плагина вместо отказа
облака (журнал — во внутреннем CHANGELOG). Поэтому валидация группы и
проверка значений белого списка сделаны в плагине, а не оставлены облаку; в
стенде такие значения стоят намеренно, хотя по документации недостижимы.

## 3. Надёжность (2.0.0)

| Ситуация | Было | Стало |
|---|---|---|
| у первого интерфейса нет IPv4-адреса: в API это пустое сообщение с `address == ""`, а не `None` | `AttributeError` и пустой inventory; в первой версии фикса — хост с `ansible_host: ""` и `ipv4: ""` | предупреждение, ВМ пропущена; `ipv4` = `null`, если публичного адреса нет |
| `primary_v4_address = None` (заглушки, старые SDK; реальный protobuf так не отвечает) | `AttributeError`, inventory пустой | предупреждение, ВМ пропущена |
| два ключа меток после нормализации совпали (`a-b` и `a_b`) | одна переменная молча затирала другую | предупреждение, в переменной остаётся последняя |
| `myyc_inventory.yml` | перехватывался плагином | обслуживается штатным yaml-плагином (нужен разделитель `_`) |
| `_yc_inventory.yml` (разделитель есть, префикса нет) | перехватывался плагином и падал на нём же | не считается своим: нужен непустой префикс перед `_` |
| отказ API: истёк IAM-токен, нет прав | наружу шёл сырой текст исключения SDK | сообщение с каталогом, причиной и подсказкой (роль `viewer`, срок жизни токена, `yc iam create-token`) |
| API вернул тот же `next_page_token` | вечный цикл, inventory висел | выход из цикла |

## 4. Упаковка (2.0.0)

- `requires-python = ">=3.11"`: `ansible-core>=2.18.18` требует Python 3.11+,
  заявленные ранее 3.8–3.10 установить всё равно было нельзя.
- Зависимость — `ansible-core`, а не мета-пакет `ansible`: плагину нужно только
  ядро (`ansible.plugins.inventory`, `ansible.errors`), а `ansible` тянет весь
  набор коллекций и имеет собственную нумерацию версий, из-за которой
  `ansible>=2.18.6` ничего не ограничивал.
- В `LICENSE` реальные правообладатели: upstream-автор и форк (в исходном файле
  стоял плейсхолдер `Your Name`, с которым файл попадал и в sdist, и в колесо).
- Лицензия описана по PEP 639 (`license = "MIT"`, `license-files = ["LICENSE"]`),
  дублирующий classifier `License :: OSI Approved :: MIT License` убран.
- В sdist входят `tests/`, `examples/`, `docs/`, а также `ansible.cfg`,
  `bootstrap.sh` и `requirements-test.txt`: без них стенд из распакованного
  архива не запускается (`run-tests.sh` читает `ansible.cfg`, `.venv` собирается
  по `requirements-test.txt`).
- Из плагина удалён мёртвый код: клиент сервиса зон (`ZoneServiceStub`,
  `ListZonesRequest`) создавался, но не использовался.
- Из `pyproject.toml` убраны неработающие и неиспользуемые части: запись
  `[project.entry-points."ansible.plugins.inventory"]` (ansible-core entry points
  для плагинов не читает вовсе), пустой `[project.scripts]`, extras `dev`
  (pytest/black/flake8/mypy не запускаются ни стендом, ни CI) и конфиги
  `[tool.black]`/`[tool.mypy]`. Единственный источник зависимостей —
  `pyproject.toml`; дублирующий `requirements.txt` удалён.

## 5. Миграция 1.x → 2.0

1. Заменить в плейбуках, ролях и `group_vars` обращения к меткам как к
   переменным: `role` → `yc_label_role`, `env` → `yc_label_env`,
   `owner_team` → `yc_label_owner_team` и так далее по тому же правилу.
2. Оставить без изменений `ansible_group` (группировка) и `ansible: false`
   (исключение ВМ из inventory).
3. Проверить `ansible_user`/`ansible_port`: они применяются, но теперь ещё и
   дублируются как `yc_label_*` — конфликтов это не создаёт.
4. Прочитать предупреждения плагина после первого запуска: всё, что попало в
   список «не применяется как служебная переменная», нужно либо перенести в
   `yc_label_*`, либо задавать в `group_vars`, а не меткой.

Альтернатива, если переписывать плейбуки не хочется: значения перенести в
`group_vars/` (или `host_vars/` по `yc_name`), а метки оставить только для
группировки и фильтрации.

## 6. Миграция 2.x → 3.0

В 3.0 имя хоста — это имя ВМ без изменений; дефисы больше не заменяются на `_`.

| Было (2.x) | Стало (3.0) |
|---|---|
| `web_1` (ВМ `web-1`) | `web-1` |
| `ansible web_1 -m ping` | `ansible web-1 -m ping` |
| `--limit web_1` | `--limit web-1` |
| `host_vars/web_1.yml` | `host_vars/web-1.yml` |
| `{{ hostvars.web_1 }}` | `{{ hostvars['web-1'] }}` |
| группы зон (`ru_central1_a`) | без изменений |
| `ansible_group: docker` → группа `docker` | группа `yc_docker` |
| `hosts: docker`, `--limit docker` | `hosts: yc_docker`, `--limit yc_docker` |
| `group_vars/docker.yml` | `group_vars/yc_docker.yml` |

Имена ВМ без дефисов не меняются. Если в каталоге были ВМ `web-1` и `web_1`,
в 3.0 это два разных хоста; в 2.x они сливались в один и одна ВМ молча
исчезала.

Группы из метки получили префикс `yc_` — это тоже 3.0: без префикса метка
вступала в вашу группу и получала её `group_vars` (секреты,
`ansible_connection: local`), а имя вида `../../outside/evil` читало файл за
пределами `group_vars`. Значение, которое уже начинается с `yc_`, даёт
`yc_yc_<значение>` и предупреждение.

## 7. Что не исправляется (осознанные ограничения)

- Параметр `cache` у `parse()` принимается для совместимости с интерфейсом
  Ansible, но не используется: inventory каждый раз запрашивается у API. Кэша
  inventory в плагине нет.
- Учитывается только первый сетевой интерфейс ВМ
  (`network_interfaces[0]`); мультиинтерфейсные ВМ получают адрес первого.
- Плагин не фильтрует ВМ по состоянию: остановленная ВМ остаётся в inventory.
- Группы `yc_*` — пространство меток, а не ваше: их создаёт `ansible_group`, и
  меткой нельзя вступить в группу без этого префикса. Обратная сторона: не
  держите секреты в `group_vars/yc_*` — такую группу может создать любая ВМ
  каталога и получить эти переменные.
- Плагин не задаёт пользователя подключения: если `ansible_user` не задан нигде,
  Ansible подключается от локального пользователя контроллера. Это поведение
  Ansible, а не плагина; имя задаётся в плейбуке (`remote_user`), ключом `-u` или
  меткой `ansible_user`.
- Если API отказал (истёк IAM-токен, не хватает прав), Ansible выводит
  предупреждение и продолжает работу с пустым inventory: так устроен разбор
  источников данных, плагин на это не влияет. Он печатает причину и подсказку, но
  код возврата остаётся успешным, поэтому в автоматике проверяйте, что inventory
  не пуст.
- Плагин ставится только каталогом: `pip install` делает его Python-модулем, но
  ansible-core загружает inventory-плагины лишь из каталогов плагинов и
  коллекций. Укажите `inventory_plugins` в `[defaults]` своего `ansible.cfg` или
  `ANSIBLE_INVENTORY_PLUGINS`.
- Дубль имени хоста в ответе API не воспроизводится и стендом не проверяется:
  имена ВМ в каталоге уникальны, поэтому в заглушке такого сценария нет.
  Предупреждение «хост уже добавлен другой ВМ» оставлено в плагине страховкой на
  случай сбоя API — молчаливой перезаписи переменных быть не должно. Граница
  ответственности: при дубле хост останется в группах зон обеих записей, потому
  что компенсация коллизий из 2.x в 3.0 удалена вместе с нормализацией имён.

## 8. Как это проверено

Отдельного облака для проверки не нужно: `tests/fake_yc/` подменяет SDK, а
`tests/run-tests.sh` прогоняет настоящий `ansible-inventory` по восемнадцати
сценариям (инъекция метками, белый список и проверка его значений, включая
непечатаемые символы, отсутствие установленного SDK, интерфейс без
IPv4 и с пустым адресом, дефисы в именах ВМ, пагинация,
`verify_file`, директивы через дефис, регистр `ansible: false`, опция `group`,
аутентификация,
отказ API, рендеринг `DOCUMENTATION` через `ansible-doc`, недопустимые значения
`ansible_group` и отсутствие наследования `group_vars` без префикса) и падает с
ненулевым кодом при регрессе.

```bash
./bootstrap.sh        # соберёт локальный .venv
./tests/run-tests.sh  # 18 сценариев, 124 проверки
```

Те же команды выполняет CI (`.github/workflows/tests.yml`): матрица Python
3.11–3.13 плюс отдельная задача из распакованного sdist — она ловит файл,
который забыли добавить в `MANIFEST.in`. Дубль имени в ответе API стендом не
проверяется намеренно: в Yandex Cloud такой ответ невозможен (§7).

Дополнительно поведение проверено на живом каталоге Yandex Cloud: инъекция
метками, белый список `ansible_user`/`ansible_port`, `ansible_host` = внутренний
IP у ВМ без публичного адреса, постраничная выдача (три страницы на две ВМ),
`ansible: false`, `YC_IAM_TOKEN` и приоритет ключа над токеном. Не
воспроизводится живьём только отсутствие IPv4-адреса на интерфейсе — в
Yandex Cloud интерфейс всегда получает внутренний адрес; этот случай покрыт
стендом.

Одна деталь про protobuf, полезная при чтении кода: незаполненное поле
сообщения приходит как пустое сообщение с `address == ""`, а не как `None`,
поэтому все проверки адресов в плагине сравнивают значение, а не объект.
